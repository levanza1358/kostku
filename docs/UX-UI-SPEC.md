# UX/UI Specification — Kostku

**Status:** Current implementation

## Principles and navigation

Kostku uses Kotlin Jetpack Compose Material 3, Indonesian copy, accessible 48dp targets, line icons with content descriptions, and explicit loading/content/empty/error states. The root has four bottom destinations: `Penghuni`, `Lokasi`, `Pembayaran`, `Pengaturan`. **The bottom navigation appears only on these four top-level tabs**; every inner page (anything with a back arrow — tenant detail, location detail and its sub-pages, forms, dialogs) renders no bottom bar. Tenant detail is a full page without bottom navigation with `Informasi`, `Riwayat Pembayaran`, and a real `Log Perubahan Data` tab fed by the tenant audit endpoint. Location detail is a full page with `Dashboard`, `Kamar`, and `Pembayaran` tabs plus a separate **Pengaturan** page.

## Design system

One shared design system keeps every screen aligned (Material 3):

- **Spacing tokens** (`ui/theme/Dimens.kt`) are the single source of truth for layout distances: `Spacing.xs/sm/md/lg/xl/xxl` (4/8/12/16/20/24dp), `Screen.edge` (16dp content inset), `Screen.gap` (12dp between blocks), `Screen.fab` (96dp list bottom clearance under a FAB) and `Screen.bottom` (24dp otherwise), and `Dimens.ButtonHeight` (52dp). Screens use these tokens instead of ad-hoc `.dp` literals.
- **App bar.** Every screen — the four main tabs and every inner page — renders the shared `AppTopBar(title, onBack, actions)`: a consistent-height `TopAppBar` on the surface color, one-line title with ellipsis, and the same `AutoMirrored.ArrowBack` "Kembali" icon. Main tabs pass `onBack = null`; the empty-state/per-screen titles (e.g. the former duplicate title in the Tentang/Bantuan/Privasi screens) are gone. `AppTopBar` owns the **status-bar (top) inset**, so the tab `Scaffold` sets `contentWindowInsets = WindowInsets(0,0,0,0)` and contributes only the bottom-navigation inset — otherwise the status bar is inset twice and every tab title sits far too low.
- **Text fields.** Every input uses the shared `AppTextField` (and `ChoiceDropdown`/`DateField`), which apply the `FieldShape` (14dp) corners, a caption label, and a consistent keyboard/IME configuration (numeric keyboards on amount/discount/count fields, "Rp " prefix on rupiah fields). The unused `SearchField` was removed.
- **Buttons.** One silhouette: primary CTAs are full-width buttons at `Dimens.ButtonHeight` with `shapes.large`; dialog confirm buttons use `SaveDialogButton` (same shape, spinner while saving). Labels are sentence case (e.g. "Generate kamar").
- **Cards and lists.** Card inner padding is uniformly 16dp (`Spacing.lg`); card lists space items by 8dp (`Spacing.sm`) and reserve `Screen.fab` bottom clearance when a FAB is present.
- **Tab strips** (`AppTabRow`) carry the same horizontal `Screen.edge` inset on the tenant, location, payment, and category screens, so the tab row lines up with the content under it.


## Screens

- **Login:** Google action, loading, failure, offline, and session-expired states.
- **Penghuni:** searchable/filterable tenant list, add action (gated on a complete setup chain), tenant detail, tenant photo. Tenant detail's gear FAB opens the **Kelola penghuni** sheet (Edit data, Perpanjang kos, Pindah kamar, Pindah tanggal, Penghuni keluar — the last one warning-tinted). **Penghuni keluar** is a two-step flow: a summary screen (Status / Kamar / Perkiraan akhir sewa) with the note that the tenant is archived automatically into the move-out history, then — after tapping **Tandai keluar hari ini** — a follow-up **Status kamar** screen asking what the room becomes via chips **Tersedia / Kotor / Maintenance** (default Tersedia), with a note that it can be changed again through Edit kamar in tab Lokasi. There is no manual archive button. Each row's trailing chip shows the **remaining lease days** (not a membership status): a green chip for ≥14 days, amber for 7–13, red for <7, and a neutral chip when no move-out date is set. A lease already past its end date reads "Lewat N hari". The phone/camera/room detail sits in the row subtitle; the day count is shown only in the chip.
- **Tenant detail:** information, payment history, remote tenant photo, and a real change-log tab from the audit endpoint. The `Informasi` tab shows a **Utilitas kamar** group (room token listrik / PDAM); a missing value reads **"Tidak tersedia"**. Location utilities are *not* shown here — they live in the location's own **Pengaturan**. Utilities are never inherited between room and location.
- **Lokasi:** location cards (logo thumbnail when set, otherwise a house icon) and add form; **Buka** opens location detail.
- **Location detail:** a full page (no bottom bar) with three tabs — `Dashboard` (occupancy progress + status chips, this-month income/expense, nearest due date, action shortcuts), `Kamar` (room list; each card offers **Detail** and **Edit** only), and `Pembayaran` (this location's income/expense ledger). A **Pengaturan** page (reached from the location) hosts **Edit info lokasi** (name, branch, address, **logo**, plus optional location utilities), **Tipe kamar**, and **Nomor kamar** (add/edit room number, type, and optional utilities); delete-location lives here too. Room creation/deletion is therefore *not* on the room list.
- **Room detail:** read-only information for one room (name, type, status, occupant, plus **Nomor token listrik** and **Nomor PDAM** when set) with an **Edit** action.
- **Room utilities:** each room may carry an optional **Nomor token listrik** and **Nomor PDAM**; each location may carry its own optional pair.
- **Rooms:** enforced setup order lokasi → tipe kamar → harga → nomor kamar; type-first setup, flexible prices, single/batch creation (only priced types selectable, with a hint when none), statuses Tersedia, Terisi, Maintenance, Kotor, and one room photo.
- **Pembayaran:** three tabs `Semua`, `Pemasukan`, `Pengeluaran`. `Semua` is a combined ledger (income + expenses, newest first) with total pemasukan and total pengeluaran cards. A single `+` FAB pops up a menu (Pemasukan/Pengeluaran, not a bottom sheet). `Pemasukan` lists server payments with status filters and manual create/edit/delete. `Pengeluaran` lists expenses (operational + tenant refund) with a type filter, manual create/edit/delete, delete confirmation, and one optional receipt photo. Every row exposes a three-dot overflow menu with **Edit** and **Hapus** (delete is red and confirmed). Payment categories come from Pengaturan.
- **Pengaturan:** Ringkasan, Profile, **Kategori** (atur kategori pemasukan & pengeluaran: layar bertab Pemasukan/Pengeluaran, daftar dengan Edit, Hapus berkonfirmasi, dan FAB tambah), **Riwayat → Penghuni keluar** (daftar penghuni yang sudah keluar, difilter per bulan dengan navigasi ‹ bulan ›; tiap baris menampilkan foto, nama, kamar, rentang tanggal, sewa, dan badge Sudah keluar; foto dapat diketuk untuk pratinjau layar penuh), Tema, Tentang Aplikasi, Open Source, Bantuan, Privasi, Keluar.

## Photo component behavior

The photo field offers `Galeri` and `Kamera`. After selection/capture it performs deterministic center cropping, shows a preview, and requires `Lanjutkan`; `Retake` discards the pending selection. EXIF orientation is honored; the longest side is resized to at most 1280 px and JPEG compression targets at most 500 KB. There is no original upload. Remote previews show `Memuat foto…`, the image, or `Foto tidak dapat dimuat.`

One active photo is allowed per tenant, room, or payment. `Ganti foto` uploads a replacement and then removes the old stored file; `Hapus foto` soft-deletes metadata and removes the file. Entity creation completes before media upload, so an upload error does not roll back or recreate the entity.

### Full-screen photo preview

Any displayed photo can be tapped to open a full-screen viewer (`ImagePreviewDialog`): a black backdrop with the image fit to screen, **pinch/double-tap to zoom (1×–6×)**, **drag to pan** (bounded so the image cannot be lost off-screen), and a **Tutup (✕)** button plus back gesture to close. It is wired to every read-only photo, including the tenant avatar (list and detail), the room thumbnail in the room list, the moved-out history avatar, and the payment/expense proof thumbnails in the `Semua`, `Pemasukan`, and `Pengeluaran` tabs (rows without a photo keep their type icon instead). In the photo **edit** surfaces (`PhotoField`, used by Edit kamar, Edit penghuni, and the payment/expense dialogs), tapping the photo opens the same viewer; the **`. . .`** button on the frame corner opens the replace/delete action sheet (`Ganti foto` / `Hapus foto`), so editing is never blocked by the preview.

Everywhere except that full-screen preview, the photo is rendered as a **circle**: the shared `ClickableRemotePhoto`/`ListPhotoThumb` clip the loaded image with `CircleShape` and `ContentScale.Crop` (so the circle is fully covered), giving the tenant list, tenant detail, room list, moved-out history, and payment/expense proof rows one consistent round avatar. Only the edit `PhotoField` frame and the preview itself are non-circular.

## Add tenant and state rules

Fields are name, phone, location, room type, available room, price, move-in, calculated/editable move-out date, discount, payment status, amount paid, and optional photo. The default payment status is `Lunas`; there is no custom move-out toggle or independent time selector.

Adding a tenant is gated on the complete setup chain (lokasi → tipe kamar → harga → nomor kamar). The "Tipe kamar" dropdown lists **only complete types** (a price AND at least one room number); incomplete types are hidden and a location with no complete type shows "Belum ada tipe kamar yang lengkap di lokasi ini. Tipe kamar wajib sudah punya harga dan nomor kamar sebelum bisa dipakai menambah penghuni." While no complete type exists, the tenant list shows a guidance empty state instead of the add form. A complete type with no *available* room still shows "Belum ada nomor kamar tersedia untuk tipe ini…". The placement form's payment section also offers **Metode pembayaran** (Tunai/Transfer/Lainnya) and **Kategori** (income categories from Pengaturan); the same payment section (discount, Lunas/Belum lunas, amount, method, category) appears on the **Perpanjang kos** screen, and every save writes an income payment.

Every remote screen supports loading, success, empty, validation error, network error, and retry. Mutations disable duplicate submission, preserve values after failure, and reload only after server success. Delete confirmations explain dependencies. Do not show HTTP codes, SQL, exception names, tokens, or raw backend messages.

## Save feedback (loading indicator and errors)

Every save action gives immediate, unmistakable feedback that a request is in flight:

- **Save button loading state.** The shared `SaveButton` (full-width forms) and `SaveDialogButton` (dialogs) swap their label for a **spinner + "Menyimpan…"** using an `AnimatedContent` fade/scale transition, and the button is disabled while saving; full-width buttons also show an indeterminate progress bar animated along the bottom edge. The same components back the Tambah penghuni form, Perpanjang kos, Edit kamar (with Hapus disabled while saving), the location dialog, Kategori, Tipe kamar/Harga, and every Pembayaran/Pengeluaran dialog — so a save is never silently "nothing happened".
- **Server errors are surfaced, not swallowed.** A failed mutation shows a persistent top **error banner** (icon + Indonesian message + `Tutup`) that stays until dismissed or the next successful action; the same message also appears as a snackbar. Server-validated conflicts (HTTP 409) read e.g. "Data bertentangan dengan data yang sudah ada. Permintaan ke server gagal. Silakan coba lagi." Form values are preserved after failure. Raw HTTP codes, SQL, exception names, tokens, and backend internals are never shown.

## Receipt (kwitansi)

Any income payment can be opened as a **receipt** (`Kwitansi`), derived entirely from the payment record — no separate document is stored. The header shows the **location logo** when one is set, otherwise a house icon, above the location name/branch/address. The body lists the receipt number, tenant, room, category, period, method, and paid date, then the **TOTAL DIBAYAR**. A status stamp reads **LUNAS** only when `status == paid`; a `partial` payment shows **SEBAGIAN** and a `pending` one **BELUM LUNAS**, so a receipt never claims a payment is settled when it is not. Two actions sit at the bottom: **Bagikan** (Android share sheet) and **PDF** (native `FileProvider` + `Intent`, no third-party library). The receipt is reachable from the payment list and from a tenant's `Pembayaran` history.

## Theme and accessibility

Material 3 light, dark, and true-black modes are persisted in preferences (`theme_mode`). Accents come from a single source (`AccentList`) offering **10 choices** — Teal, Biru, Indigo, Ungu, Merah Muda, Merah, Oranye, Kuning, Hijau, Cyan — persisted under the `accent` key. Each accent has **per-mode shades**: a darker tone on light mode (white on-accent text) and a lighter tone on dark/true-black (near-black on-accent text), so accent text is never dark-on-dark. All related Material roles are derived from the chosen accent (`onPrimary`, `primaryContainer`/`secondaryContainer` tonal surfaces, etc.). The **Tema** screen shows a **live preview** rendered from the real `ColorScheme` (section title, primary/tonal buttons with their on-accent text, status badges, body text) and an accent grid whose swatches use the current mode's shade with a selection ring. Status is communicated with text as well as color. Labels, TalkBack descriptions, contrast, and system font scaling remain usable.
