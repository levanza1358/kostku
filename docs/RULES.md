# Rules — Kostku

1. Google Login is mandatory; every business request is ownership-scoped by the server.
2. Access/refresh tokens are never logged. Access tokens refresh automatically once; failed refresh ends the session with Indonesian handling.
3. Root navigation has exactly four destinations: Penghuni, Lokasi, Pembayaran, Pengaturan. Tenant detail has no bottom navigation; location detail leads to room management.
4. All user-visible text is Indonesian, including validation, loading, network, empty, and session messages.
5. Server data is authoritative. Refresh after successful mutations; preserve forms after failure.
6. A property requires name and address. Room statuses are Tersedia/vacant, Terisi/occupied, Maintenance/maintenance, and Kotor/dirty.
7. Batch rooms accept 1–100 unique names and commit atomically.
8. Ordering is mandatory: lokasi → tipe kamar → harga → nomor kamar. Room types precede rooms, and a price must exist before a room number can be created (the server rejects room creation when the room type has no price; the batch form only offers types that already have a price). Only **complete** room types — those with a price AND at least one room number — may be chosen when adding a tenant; incomplete types are hidden from the placement form, which is itself gated until at least one complete type exists. Prices are normalized by occupancy and duration (day/week/month/year).
9. Adding a tenant requires name, location, room type, available room, and price. Phone is optional.
10. Move-in defaults to device date/time. Move-out is derived from price duration and may be edited by tapping the date; there is no custom toggle or separate end time.
11. Initial payment defaults to Lunas, with a payment method and income category. Discounts, rent, due day, amount paid, and payment status are server-validated.
12. Tenant placement, the initial income payment (always written — full amount when Lunas, otherwise the entered partial/zero amount as `partial`/`pending`), and room occupation are transactional.
13. Payment records (income) are manual and use decimal money. Expenses (outflows) live in `expenses` with `kind` `operational` or `refund`; refunds link to a tenant. The Pembayaran screen shows `Semua` (combined ledger), `Pemasukan`, and `Pengeluaran`. Each income/expense row exposes a three-dot overflow menu with **Edit** and **Hapus**; both edits and deletions are server-validated, and deletion (which removes the record permanently) is confirmed. Income/expense **categories are user-managed** (Pengaturan → Kategori; global per account, `categories` table) and are referenced in records **by name**, so editing the list does not rewrite existing records.
13a. Every lease extension ("Perpanjang kos") updates the tenant (`move_out_date`, `monthly_rent`) **and records one income payment** transactionally via `POST /tenants/{id}/extend` — a lease is never extended without a matching payment row. `PATCH /tenants/{id}` never writes a payment.
14. Photo source choice is Galeri or Kamera. Preview uses deterministic center crop and explicit continue/retake.
15. Client photos use EXIF orientation, longest side ≤1280 px, and target ≤500 KB. The original is not uploaded.
16. Tenant photos, room photos, payment proof photos, and expense receipt photos use one active photo per entity. Replacement adds new metadata before removing the old file; delete soft-deletes metadata and removes its file.
17. Entity creation precedes media upload. Upload failure must not create a duplicate entity and does not roll back the entity.
18. Server validates ownership, actual MIME (JPEG/PNG/WebP), dimensions, and bytes. Media bytes are VPS filesystem files; MySQL stores metadata/path, never blobs.
19. Remote previews expose loading and error states. Destructive actions require confirmation; status is conveyed by text and color; touch targets are at least 48dp.
20. Tenant change events (create, update, move, move-out, extend) are recorded in `tenant_audit_log` and shown in the `Log Perubahan Data` tab via `GET /tenants/{id}/audit`; audit writes never break a tenant mutation if the table is missing.
21. Production uses native PHP/PDO with MySQL/MariaDB. Deploy the media migration, environment values, writable storage, and `.htaccess`; upload `index.php` manually. Node/PostgreSQL is legacy.
22. Deleting an entity purges its media — the `media` metadata rows **and** the physical files. Hard deletes (`DELETE /payments/{id}`, `DELETE /expenses/{id}`, `DELETE /rooms/{id}`) and tenant archive (`DELETE /tenants/{id}`) call `mediaPurge(type, id, ownerId)`; an entity and its photos are never left half-deleted. Media files are served by the CDN/proxy with a long cache (1 month), so a URL may briefly still serve a deleted file until that cache expires — the origin file is already gone.
23. Every save shows progress and never fails silently. Save buttons (`SaveButton`, `SaveDialogButton`) show a spinner + "Menyimpan…" and disable while the request is in flight; a failed mutation surfaces a persistent top **error banner** (icon + Indonesian message + `Tutup`) plus a snackbar, preserves the form, and clears on dismiss or the next success. Raw HTTP codes, SQL, exception names, tokens, and backend internals are never shown.
24. Every displayed photo opens a full-screen preview on tap (`ImagePreviewDialog`): black backdrop, image fit to screen, pinch/double-tap **zoom** (1×–6×, bounded), **drag to pan** (clamped), and a `Tutup` (✕) button + back gesture to close. Remote photos are its target everywhere (tenant avatar, room list, payment/expense proof thumbnails, moved-out history). In the `PhotoField` **edit** surfaces the tap opens the same viewer while the frame's `. . .` button opens the `Ganti foto`/`Hapus foto` sheet, so previewing never blocks editing. **Outside the full-screen preview every photo display is a circle** — the shared `ClickableRemotePhoto`/`ListPhotoThumb` clip the loaded image with `CircleShape` and `ContentScale.Crop` by default (tenant list, room list, tenant detail, moved-out history, payment/expense proof rows); only the edit `PhotoField` frame and the preview itself are non-circular.
25. Accents are defined once (`AccentList`) with a **per-mode shade** — a darker tone for light mode and a lighter tone for dark/true-black — and every derived Material role (`onPrimary`, containers) is computed from the chosen accent. An accent color is never painted as text on a background of similar luminance, and the Tema screen always previews the real scheme live. New accents are added to `AccentList` only (no duplicated name lists).
26. Marking a tenant as moved out (`POST /tenants/{id}/move-out`) is **atomic** and only valid for an `active` tenant (409 otherwise): it archives the tenant automatically, applies the requested **`room_status`** to the room (`vacant`/Tersedia default, `dirty`/Kotor, or `maintenance` — chosen on a follow-up screen; anything else is rejected 400), writes a `moved_out` audit entry, and records a durable **`tenant_move_out_history`** snapshot (name, phone, room, dates, rent). There is no separate manual archive action. The history survives later edits and archiving and is read by month (`GET /tenants/move-out-history?month=YYYY-MM`), reaching the user through `Pengaturan → Riwayat → Penghuni keluar` with prev/next month navigation.
27. One design system governs all layout (`ui/theme/Dimens.kt`). Screens use the `Spacing`/`Screen`/`Dimens` tokens — never ad-hoc `.dp` literals — for insets, gaps, list spacing, FAB clearance, and button height. Every screen renders the shared `AppTopBar` (never a raw `TopAppBar` or an in-body title), every input uses `AppTextField`/`ChoiceDropdown`/`DateField` (never a raw `OutlinedTextField`), and primary actions use the shared button silhouette (`SaveButton`/`SaveDialogButton`, `shapes.large`, `Dimens.ButtonHeight`, sentence-case labels).
28. Remote photos are loaded through the app-wide **Coil** `ImageLoader` (`KostkuApp`, `SingletonImageLoader.Factory`) — never a raw `URL.openConnection()`/`HttpURLConnection` or per-screen decode. The singleton caches in memory (20% RAM) and on disk (128 MB under `cache/image_cache`) and fetches over a shared OkHttp client that honours the media CDN's `Cache-Control`/`ETag`, so a photo is downloaded **once** and re-served from cache — the rule exists to keep the app's data/quota use low while staying fully synced. New photo surfaces use the shared `RemotePhotoPreview`/`ClickableRemotePhoto`/`ListPhotoThumb` (circle by default) rather than opening their own connection.
29. Application data is read through the **single `GET /snapshot`** endpoint, not by fanning out many per-entity requests. The client stores the snapshot and its `ETag` locally (`SnapshotCache`: `kostku_snapshot.json` + `kostku_cache` prefs) and revalidates with `If-None-Match`, so an unchanged dataset costs a **304** (no body) and a changed one a fresh `200`; the server gzips JSON. Cache is shown first for instant, offline-tolerant rendering (only a 401 ends the session). A mutation always changes the data and therefore the `ETag`, so a reload after a save is never stale. The gzip/`ETag`/304 behaviour is part of the deployed backend (`public/index.php`, `config/bootstrap.php`); `insertSnapshot()` (in `bootstrap.php`) is the single source of that payload.
30. Electricity/water utilities are **optional free text** on both locations (`properties.token_listrik`/`pdam_number`) and rooms (`rooms.token_listrik`/`pdam_number`), stored as text so leading zeros survive — never reformatted as a number. They are **not inherited** between levels: the tenant detail lists the room's utilities and the location's utilities as two separate groups, and any missing value is shown as **"Tidak tersedia"** rather than left blank or hidden. Utility fields are labelled optional and carry no required marker.
31. A location may carry one **logo** (`media` `entity_type='property'`, category folder `lokasi`, the same one-active-photo pipeline as other media). The logo appears on the location list and on the **receipt**; when a location has no logo the receipt and list fall back to the built-in **house icon**, so a receipt header is never empty or broken.
32. A **receipt (kwitansi)** is derived entirely from a single payment record — there is no `/receipt` endpoint and no stored document. The status stamp reads **LUNAS** *only* when `status == paid`; a `partial` payment reads **SEBAGIAN** and a `pending` one **BELUM LUNAS**, so a receipt can never claim a payment is settled when it is not. `Bagikan`/`PDF` use Android's native share (`FileProvider` + `Intent`), not a third-party library.
